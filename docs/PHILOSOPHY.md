# Abyss Philosophy

> **Build. Learn. Explore.**

Abyss is my playground for building CLI programs, experimenting with software ideas, and learning by actually making things.

It exists because I don't want to have dozens of unfinished projects scattered around while constantly starting something new.

Abyss gives those experiments a home.

---

## 1. Abyss Is a Playground

Abyss does not need to become a perfect product.

It is allowed to be:

* experimental
* ugly
* incomplete
* rewritten
* broken
* improved

The goal is **learning through building**, not creating perfect software from the beginning.

---

## 2. Nothing Gets Added Without a Reason

Do not add a feature just because it sounds cool.

A feature should solve one of these:

* a problem I actually encountered
* a problem caused by the current architecture
* a learning goal I intentionally want to explore

If a feature doesn't have a reason, it belongs in an idea list—not in Abyss.

> **Abyss is not a collection of every programming idea I have.**

---

## 3. Standalone Projects Stay Standalone

Abyss can absorb useful projects, but adding a project to Abyss does not erase its original identity.

If I build a Todo app, Notes app, DNS tool, or another experiment and later integrate it into Abyss:

**the original project should still be understandable and recoverable.**

Never delete a standalone project just because it became an Abyss module.

---

## 4. Learn Before Abstracting

Do not build abstractions for problems that haven't appeared yet.

First:

```text
Build → Use → Find a problem → Understand it → Improve it
```

Not:

```text
Imagine every possible problem → Build a framework → Never finish it
```

Abyss should grow from **real problems**, not hypothetical ones.

---

## 5. Keep the Core Small

The core of Abyss should remain simple.

Plugins should provide functionality.

The core should mainly provide the environment in which that functionality lives.

If a plugin can solve a problem without modifying the core, prefer that solution.

---

## 6. Understand What I Build

Using libraries is allowed.

Copying architecture without understanding it is not the goal.

When something important is added to Abyss, I should eventually understand:

* what it does
* why it exists
* how it communicates with the rest of Abyss
* what problem it solves

I don't need to understand every line immediately.

But I should be able to learn it later.

---

## 7. Refactoring Is Part of Building

Code does not need to be perfect before it is useful.

When the project becomes difficult to extend, understand, or debug, that is a signal to refactor.

Refactoring should happen when:

> **The benefit of cleaning the existing structure becomes greater than the benefit of adding another feature on top of it.**

Don't refactor merely because the code looks imperfect.

Don't avoid refactoring when the current design is actively slowing development.

---

## 8. Don't Turn Abyss Into Its Own Problem

Abyss exists to help me build things.

If maintaining Abyss starts consuming more time than actually building things with it, something has gone wrong.

The solution is usually:

**simplify.**

Not another abstraction.

---

## 9. Small Progress Counts

Abyss is also a learning environment.

A small feature completed is better than a huge architecture planned.

A working ugly solution is often more valuable than a beautiful unfinished one.

Progress can look like:

```text
write → break → investigate → fix → understand
```

That is still progress.

---

## 10. Experimentation Is Allowed

Some experiments will fail.

Some ideas will be stupid.

Some code will eventually be deleted.

That's fine.

A failed experiment that taught me something is not wasted work.

> **Abyss is allowed to contain dead ends.**

---

## 11. Build for Myself First

Abyss does not need to satisfy everyone.

It should first solve problems that **I actually have**.

If other people eventually find it useful, that's a bonus.

The project should not become complicated just to look impressive to other developers.

---

## 12. The Main Rule

When I am unsure whether something belongs in Abyss, ask:

> **"What problem am I solving?"**

If I cannot answer that clearly, don't build it yet.

---

# The Abyss Rule

**Build things because I want to understand them.
Keep things because they are useful.
Refactor things when they become a problem.
Remove things when they no longer serve a purpose.**

And most importantly:

> **Abyss is a place to explore, not another place to get lost.**
